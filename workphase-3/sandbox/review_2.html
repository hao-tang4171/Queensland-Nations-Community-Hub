FETCH POST Review 2

This task was about understanding how a form actually submits to the course API using fetch and POST. I didn't use AI for this one.

How this connects to A2

  • This is the part that makes the A2 subscription form actually do something. Before, it was just a visual mockup.
  • The form fields and styling still match A2 — same fonts, same colours, same feel.
  • Connecting to the API is what turns the page from a static design into a working part of the platform.

What this task adds beyond A2

  • The form actually submits to the course API now — A2 didn't have any of that working.
  • I had to add the bits the API needs: an authentication header, a JSON body, and proper handling of what the server sends back.
  • The form and the API call started to feel like two separate things, which made me think about keeping them in separate files later.

Feedback and accessibility

If a form submits but doesn't say anything back, the user is left guessing. I added a small status message under the form so people see whether it worked or not. I also disabled the submit button for a moment after clicking, so nobody double-submits by accident.

Decision

I chose not to use AI for this one. I wanted to actually understand how POST and fetch work, not just get to a finished result. So I added each piece step by step, checked what was happening in DevTools, and only moved on once I could see why it was working.

Issues found while implementing

  • My first submissions got rejected because I hadn't added the authentication headers properly.
  • I wasn't sure whether the request body should be a plain JS object or a JSON string. It turned out to matter, and I only figured it out by testing.
  • I was handling the response at the wrong step, so my "success" code ran before the server had actually replied.

Cause and how I verified the fix

Each problem came down to a small gap in what I understood — wrong headers, wrong body format, or the promise chained in the wrong place. I just opened DevTools, looked at the request and response in the Network tab, changed one thing, tested, and kept the change only if it actually worked. I went round this loop several times before the submission went through cleanly. It was slower than just copying a working answer would have been, but I genuinely understand the request now, which I think will pay off when I need to do harder things with the API later.
